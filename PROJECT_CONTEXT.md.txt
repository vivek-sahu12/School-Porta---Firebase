1. PROJECT IDENTITY
================================================================================

- Project Name: School Data Portal ("school-data-portal" in package.json; displayed as "School Portal" and "School Data Portal - Admin").
- Project Purpose: A centralized, multi-tenant, offline-first school data and institutional administration system designed to manage educational institutions, student demographic/academic records across disparate datasets (School Data, UDISE, and 3.0), staff user accounts, granular permissions, concurrent device limits, and active connected device sessions.
- Main Problem the Project Solves:
  1. Resolves fragmentation across multiple government and institutional student data formats (internal School Data records, national UDISE compliance registries, and State Portal 3.0 enrollment records).
  2. Eliminates unauthorized credential sharing and unmonitored concurrent logins by enforcing strict, configurable per-account concurrent device limits (1 to 15 devices) and real-time session tracking.
  3. Provides resilient offline-first usability for schools in areas with intermittent internet connectivity via IndexedDB caching and an offline mutation/synchronization queue.
  4. Delivers two isolated control panels: a master Super Admin Control Panel for overarching institutional oversight and a dedicated School Portal for campus-level data exploration and staff management.
- Intended Users:
  1. Super Administrators (Master administrative operators managing the entire multi-school network, registering schools, creating primary accounts, revoking access, monitoring live sessions, and auditing system events).
  2. School Primary Administrators / Institutional Accounts (Principal or administrative leadership account representing an individual school).
  3. School Staff / Teachers / Operators (Sub-accounts under a specific school with role-based feature permissions such as Editable, Add Student, Delete Student, Excel Export, and Reports).
- Target Organizations / Schools: K-12 educational institutions, primary and secondary schools, high schools offering classes from Nursery through Class 12, and state/national education network hubs.
- Current Development Stage: Production-grade MVP / Active Functional Baseline (Frontend-driven architecture connected to live Firebase Authentication, Cloud Firestore, and local IndexedDB; student datasets are generated via an in-memory & IndexedDB caching engine; backend server is absent).
- Main Application Type: Progressive Web Application (PWA) / Multi-Page Application (MPA) built with modern ES modules, Vanilla JavaScript, and native CSS3, bundled and served via Vite.
- Frontend/Backend Architecture:
  - Frontend: Pure Vanilla JavaScript (ES modules) with HTML5 and semantic CSS3. No heavy JS framework (no React, Angular, or Vue).
  - Backend: Serverless / Backend-as-a-Service (BaaS). The client application communicates directly from the browser to Google Cloud Firebase services (Firebase Authentication and Cloud Firestore). No Node.js, Express, Python, or Go custom backend API exists.
- Deployment / Hosting Setup: Configured for static hosting (Vite build output to dist/ directory; previously adapted for GitHub Pages / Firebase Hosting static deployment with relative path base `./`).
- Repository / Project Structure: Single root directory containing Vite configuration, package definitions, two entry portals (`index.html` for School Portal and `admin/index.html` for Super Admin), modular CSS stylesheets, shared application icons, and an organized `js/` directory split into core modules (`firebase.js`, `offline-store.js`, `session-manager.js`, `school-config.js`, `image-resolver.js`), admin controllers (`js/admin/`), school controllers (`js/school/`), and user auth (`js/user/`).
- Known Project Goals Found in Codebase:
  - Integration of live CSV/Excel ingestion pipeline for student records (Student Data Module placeholder currently active).
  - Expansion of fee management and student billing ledger.
  - Native PDF report generation for student rosters and school cards.
  - Cloud Functions migration for privileged operations (e.g., automated session garbage collection and administrative user provisioning).

4. APPLICATION FLOW — END TO END
================================================================================

1. Initial Application Load:
   - User opens either the root URL (`./index.html`) or Admin URL (`./admin/index.html`).
   - Browser evaluates import maps and loads native ES modules.
   - `js/firebase.js` initializes the Firebase App singleton and sets auth persistence to `browserLocalPersistence`.
2. Routing & Entry Portals:
   - Static multi-page routing handled via separate HTML files:
     - School Portal Login: `index.html`
     - School Portal Dashboard: `dashboard.html`
     - Super Admin Login: `admin/index.html`
     - Super Admin Dashboard: `admin/dashboard.html`
   - Internal tab/view switching on both dashboards is executed via client-side DOM manipulation (toggling `.active` classes on `<section>` views and `<button>` navigation elements) without full page reloads.
3. Login Screen Execution:
   - For School Users (`index.html`): Form `#school-login-form` receives Login ID/Email and Password.
   - For Super Admin (`admin/index.html`): Form `#login-form` receives Master Admin Email and Password.
4. Authentication:
   - Calling `signInWithEmailAndPassword(auth, email, password)`.
   - On failure: Maps Firebase error codes (`auth/invalid-credential`, `auth/user-disabled`, etc.) to clear human-readable alerts.
5. User Verification:
   - In School Login (`js/user/login.js`):
     - Checks `users/{uid}` in Cloud Firestore.
     - If document does not exist or lacks `schoolId`: Access is denied with "Access Denied: This account is not registered with any School Institution." and `signOut()` is executed.
     - If `userData.status === "Inactive"`: Login is rejected with "Your school account has been deactivated."
     - Verifies `schools/{schoolId}`: If `schoolData.status === "Inactive"`, login is rejected with "This School Institution is currently inactive."
   - In Super Admin Login (`js/admin/login.js`):
     - Validates that `user.uid === "FSe6FQsJrKaDVqqjcO4jv2EIkfp2"`. If UID does not match, sign-out is triggered and access is denied.
6. Role Detection & Account Level Hierarchy:
   - Level 1: Master Super Admin (Identified strictly by UID `FSe6FQsJrKaDVqqjcO4jv2EIkfp2`). Full system control over all schools, accounts, sessions, and settings.
   - Level 2: Primary School Account (Document in `users/{uid}` with `type: "school"`, associated with `schoolId`). Represents the institution itself, possesses institution-wide administrative permissions, and can edit school metadata.
   - Level 3: Additional School User (Document in `users/{uid}` with `type: "user"`, associated with `schoolId`). Represents a teacher/staff member with individualized permissions.
7. Admin Flow:
   - Super Admin lands on `admin/dashboard.html`.
   - `js/admin/dashboard.js` confirms auth state and UID match.
   - Firestore listeners attach to `schools`, `users`, `sessions`, and `admin_logs`.
   - Admin can view overall metrics, browse schools, drill into School Details (5 sub-tabs), edit campus information, manage accounts, configure device limits and permissions, monitor live sessions across all schools, force-terminate sessions, activate/deactivate schools, and view real-time audit logs.
8. Normal School-User Flow:
   - Authenticated user is redirected to `dashboard.html`.
   - `js/school/dashboard.js` reads cached user and school data from IndexedDB for instant UI rendering.
   - Verifies device session and registers active session in Firestore.
   - Initializes 24-hour inactivity monitor and network connectivity listener.
   - Starts a 60-second periodic heartbeat updating `sessions/{sessionId}.lastActive`.
   - Real-time snapshot listeners attach to the session document, user document, and school document to catch administrative revocation instantly.
9. Dashboard Loading:
   - School Portal UI (`js/school/school-ui.js`) renders school branding (name, unique ID, logo via `image-resolver.js`).
   - `student-service.js` loads or generates dataset records for `school_data`, `udise`, and `three_point_zero`.
   - Computes total records, class strength breakdown, gender ratio, and caste categories (GEN, OBC, SC, ST).
10. Database Reads:
    - Schools: `schools/{schoolId}` (metadata, class range, subjects, logo URL, status).
    - Users: `users/{uid}` (account profile, school linkage, permissions, device limit, status).
    - Sessions: `sessions` query where `schoolId == currentSchoolId` and `status == "active"`.
    - Local Cache: Reads from IndexedDB `SchoolPortalOfflineDB` (`cache` store).
11. Database Writes:
    - Enrolling/updating school: `setDoc(doc(db, "schools", schoolId), ...)`
    - Updating primary school account or user: `setDoc(doc(db, "users", uid), ...)`
    - Registering session: `setDoc(doc(db, "sessions", sessionId), ...)`
    - Heartbeat: `updateDoc(doc(db, "sessions", sessionId), { lastActive: serverTimestamp() })`
    - Terminating session: `updateDoc(doc(db, "sessions", sessionId), { status: "terminated", logoutTime: serverTimestamp() })`
    - Logging audit: `setDoc(doc(adminLogsCol), ...)`
    - Deleting school: `deleteDoc(doc(db, "schools", schoolId))` and `deleteDoc(doc(db, "users", schoolUid))`
    - Offline fallback: Writes to IndexedDB `pendingQueue` when offline.
12. Data Displayed on Screen:
    - Institutional header (School Name, ID, Logo, status badge).
    - Dataset selector buttons and count pills.
    - Class-wise student distribution cards with click-to-filter capability.
    - Gender comparison bar (Boys vs Girls percentages and counts).
    - Category distribution cards (GEN, OBC, SC, ST).
    - Filtered Student List feed with search input.
    - Student profile modal/view displaying basic data, parent details, and registry IDs.
    - Tables for School Users and Active Connected Sessions.
13. Logout Flow:
    - Explicit Logout: User clicks "Logout" -> `performExplicitLogout()` marks Firestore session as `status: "logged_out"`, clears `localStorage` and `sessionStorage`, wipes local IndexedDB cache via `clearOfflineCache()`, calls `signOut(auth)`, and redirects to `index.html`.
    - Forced Logout / Revocation: Triggered by 24h inactivity, admin termination, or account/school deactivation -> `performForcedLogout()` signs out and redirects to `index.html?reason=force_logout` or `?reason=inactivity` displaying an informative alert banner.
14. Error Handling:
    - Authentication errors converted to user-friendly messages via `getFriendlyErrorMessage()`.
    - Network drops automatically switch UI badge to "Offline (Working from local cache)".
    - Failed Firestore writes offline are captured and stored in IndexedDB `pendingQueue`.
15. Loading States:
    - Fullscreen loaders (`#page-loader`) with spinners on initial page loads and transitions.
    - Button spinners (`.btn-spinner`, `.spinner`, `.is-loading`) during form submissions.
    - Topbar network badge showing "Syncing...", "Online", or "Offline".
16. Protected Routes & Redirects:
    - Unauthenticated visitors on `dashboard.html` or `admin/dashboard.html` are automatically redirected to `index.html` or `admin/index.html`.
    - Non-admin users attempting to open `admin/dashboard.html` are explicitly signed out and redirected with "Access Denied".

5. AUTHENTICATION & AUTHORIZATION
================================================================================

- Login Provider: Firebase Authentication Email/Password.
- Authentication Method: Direct client SDK call `signInWithEmailAndPassword(auth, email, password)`.
- Session Persistence: Explicitly configured as `browserLocalPersistence` across all portals, ensuring login persists across browser tab closures and reloads until explicitly logged out or expired.
- User IDs / UIDs: Standard Firebase Authentication UIDs (alphanumeric string generated by Firebase, e.g., `FSe6FQsJrKaDVqqjcO4jv2EIkfp2`).
- 3-Tier Role Management Architecture:
  1. Super Admin:
     - Identification: Hardcoded Master UID `FSe6FQsJrKaDVqqjcO4jv2EIkfp2` verified in `js/admin/login.js`, `js/admin/dashboard.js`, and `js/admin/firestore-service.js`.
     - Privileges: Unrestricted global access. Can create/edit/delete schools, add existing Firebase accounts, toggle operational status, configure permissions, modify device limits, force-logout sessions across any school, and inspect audit logs.
  2. School Account (Primary Institutional Account):
     - Identification: Record in `users/{uid}` where `type === "school"` and `schoolId` matches the school entity.
     - Privileges: Primary owner of the school's data. Has full default permissions (editable: true, addStudent: true, deleteStudent: true, excelExport: true, reports: true). Can edit school profile metadata, class ranges, senior subjects, and manage additional school users.
  3. School User Account (Staff / Operator):
     - Identification: Record in `users/{uid}` where `type === "user"` and `schoolId` links to a specific school.
     - Privileges: Granular permissions determined by boolean flags in `users/{uid}.permissions`:
       - `editable` (boolean): Permission to edit student/school records.
       - `addStudent` (boolean): Permission to register new students.
       - `deleteStudent` (boolean): Permission to delete student records.
       - `excelExport` (boolean): Permission to download records in Excel/CSV format.
       - `reports` (boolean): Permission to view analytics and reports.
- Device Limit & Concurrent Access Enforcement:
  - Each account (`users/{uid}`) contains a configurable `deviceLimit` (integer, range 1 to 15, default: 3).
  - During login in `js/user/login.js`:
    1. The client queries Firestore: `sessions` collection where `userUid == user.uid` and `status == "active"`.
    2. If `activeSessionsSnap.size >= deviceLimit`, login is BLOCKED immediately.
    3. Firebase `signOut()` is called and the user receives the error: "Maximum device limit reached (X devices). Please log out from another device."
    4. If within limits, a new session document (`SES_<timestamp>_<random>`) is created with `status: "active"`.
- Real-Time Session Invalidation & Force Logout:
  - While logged into `dashboard.html`, a real-time `onSnapshot` listener watches `sessions/{currentSessionId}`.
  - If a Super Admin or School Admin terminates the session, `sessionData.status` changes to "terminated".
  - The snapshot listener fires immediately, calls `performForcedLogout()`, clears client credentials, and redirects to login with an alert.
  - Similar real-time listeners watch `users/{uid}` and `schools/{schoolId}` to force immediate logout if the account or school is marked "Inactive".
- 24-Hour User Inactivity Expiration:
  - Implemented via `js/session-manager.js`.
  - Genuine user interaction events (`mousedown`, `keydown`, `touchstart`, `scroll`, `input`, `click`) update `localStorage.getItem("portal_last_activity")`, throttled to once every 15 seconds.
  - Merely opening or reloading a browser tab does NOT refresh this timestamp.
  - A background interval checks every 30 seconds: if `Date.now() - lastActive >= 24 * 60 * 60 * 1000` (24 hours), session expiration is triggered.
- Session Retention Policy:
  - To prevent unbounded accumulation of obsolete session documents in Cloud Firestore, `enforceUserSessionRetention(userUid, 3)` strictly retains only the newest 3 session records per user.
  - Any 4th or older session documents for that specific UID are physically deleted from Firestore.
  - Super Admin dashboard runs an additional routine `cleanupOldSessions()` purging any terminated/logged-out sessions older than 48 hours.
- Custom Claims / Backend Verification:
  - NOT VERIFIED / NOT FOUND IN PROJECT. Custom claims via Firebase Admin SDK are not used; role checks are performed client-side against Firestore document fields and the hardcoded Super Admin UID.

6. DATABASE ARCHITECTURE
================================================================================

- Database Type: Cloud Firestore (NoSQL Document-Oriented Database) supplemented by client-side IndexedDB for local caching.
- Firebase Project ID: `school-data-portal-firebase`
- Data Model Philosophy: Flat top-level collections with relational foreign keys (`schoolId`, `userUid`). Multi-tenant isolation is enforced logically via query filters (`where("schoolId", "==", currentSchoolId)`).

--------------------------------------------------------------------------------
COLLECTION: `schools`
--------------------------------------------------------------------------------
- Document ID: Canonical School ID (e.g., `SCHOOL001`, uppercase string).
- Purpose: Authoritative institutional entity record containing school identity, campus metadata, and academic configuration.
- Fields & Data Types:
  - `schoolId` (string): Unique uppercase institutional identifier (e.g., "SCHOOL001"). Matches document ID.
  - `name` (string): Official name of the school (e.g., "Springfield Public School").
  - `schoolName` (string): Duplicate mirror of `name` for backwards compatibility.
  - `firebaseUid` (string): Firebase Auth UID of the primary school account (Level 2).
  - `adminEmail` (string): Contact/login email address for school administration.
  - `phone` (string): Optional contact phone number for the school institution.
  - `status` (string): "Active" | "Inactive". Controls whether institutional access is permitted.
  - `address` (string): Physical campus address.
  - `logoUrl` (string): Direct image URL or Google Drive link to the school's logo.

14. SECURITY ARCHITECTURE
================================================================================

- Authentication Layer: Firebase Authentication Email/Password with client persistence set to `browserLocalPersistence`.
- Role-Based Access Control (RBAC):
  - Super Admin: Hardcoded UID check (`SUPER_ADMIN_UID = "FSe6FQsJrKaDVqqjcO4jv2EIkfp2"`).
  - School Accounts: Document check in `users/{uid}` matching `type === "school"`.
  - School Users: Document check in `users/{uid}` matching `type === "user"`.
- School-Level Data Isolation:
  - Handled at query level: School dashboard queries filter strictly by `where("schoolId", "==", currentSchoolId)`.
  - Offline IndexedDB caching prefixes student datasets with `schoolId` (e.g., `students_sd_SCHOOL001`).
- Active Device Session Limiting:
  - Login queries existing active sessions and blocks authentication if active count >= `deviceLimit`.
  - Client heartbeat continuously monitors and reports device state.
- Inactivity Security:
  - Client automatically expires credentials and executes forced logout after 24 hours of user inactivity.
- Sensitive Data Handling:
  - Passwords are never stored in Firestore; authentication credentials are submitted directly to Firebase Auth.
  - Secret API keys are not exposed in plaintext reports.

16. KNOWN ISSUES / WARNINGS
================================================================================

1. Missing `firestore.rules` in Repository:
   - Firestore security rules are not committed to source control. If database rules in the Firebase console are left in test mode or open, unauthorized clients could manipulate documents directly.
2. In-Memory / Seed Student Data:
   - Student records in `js/school/student-service.js` are currently generated via a deterministic generator based on the school's class range and cached in IndexedDB. While this provides instant, rich analytics and demonstration data, persistent student CRUD operations directly against a Firestore `students` collection are not yet wired.
3. Super Admin Hardcoded UID:
   - The master Super Admin UID (`FSe6FQsJrKaDVqqjcO4jv2EIkfp2`) is embedded in client files. While effective for frontend routing, it should be reinforced with custom claims and server-side rules.
4. Excel Import / Export Libraries Not Installed:
   - The UI contains buttons and toggles for Excel export and student data import, but spreadsheet libraries (e.g., `xlsx` or `papaparse`) are not yet installed in `package.json`.
5. Local File Protocol (`file:///`) Limitation:
   - Because the project uses native ES modules (`import`/`export`), loading the HTML files directly via `file:///` causes browser CORS errors. Must be served using a local HTTP server (e.g., `npm run dev` via Vite, or VS Code Live Server). A detection banner is present in `admin/index.html`.

- Where Database Logic Belongs:
  - Administrative database operations belong exclusively in `js/admin/firestore-service.js`.
  - School portal database and caching operations belong in `js/school/school-ui.js` and `js/school/student-service.js`.
  - Universal session and auth lifecycle logic belongs in `js/session-manager.js`.
  - Low-level IndexedDB caching logic belongs in `js/offline-store.js`.

  - All Firebase initialization, authentication instances, and Firestore instances MUST be imported from `js/firebase.js`. Never call `initializeApp()` elsewhere.

  - School ID: Uppercase alphanumeric (e.g., `SCHOOL001`).
  - Session ID: Uppercase prefix with timestamp: `SES_<timestamp>_<random>`.
  - Device ID: Uppercase prefix: `DEV_<random>`.
  - HTML IDs: kebab-case (e.g., `sidebar-user-email`, `login-submit-btn`).
  - CSS Classes: kebab-case with BEM-style modifiers (e.g., `badge-active`, `btn-primary`, `status-online`).
- Critical Files to Never Modify Casually:
  - `js/firebase.js`: Foundation for all auth and database instances.
  - `js/session-manager.js`: Controls 24h inactivity expiration, session cleanup, and forced logout.
  - `js/school-config.js`: Central rank calculation; modifying ranks breaks class range validations.
